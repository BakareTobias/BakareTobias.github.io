Vision-Guided Pick-and-Place Simulation

A simulated 7-DOF Franka arm that finds blocks by color with a camera, then picks them up and drops them in a bin.

View on GitHub ↗

Role

Solo project

Robot

Franka arm, 7-DOF

Stack

ROS2 Jazzy, MoveIt2, Gazebo

Languages

C++ and Python

The goal

Build a complete perception-to-motion pipeline in simulation. That meant modelling the arm, controlling it with MoveIt2, and then letting a camera decide where it should go, so the robot can pick up three blocks from a table and place them in a bin behind it without hard-coded positions.

How it works

The pick-and-place task runs as a five-stage pipeline:

  1. Camera: a simulated camera in Gazebo looks down at the table.
  2. Color detection: a vision node finds each block in the camera image.
  3. TF transform: block positions are converted from the camera frame into the robot's frame.
  4. MoveIt planning: MoveIt2 plans arm motions to each block and then to the bin.
  5. Execution: a C++ node runs the pick and place for all three blocks.

The project is split into seven ROS2 packages:

  • panda_description: URDF files, meshes and models
  • panda_bringup: launch files, configs, RViz and Gazebo world files
  • panda_controller: slider control launch file and node
  • panda_moveit_config: config and launch files generated by the MoveIt Setup Assistant
  • panda_vision: the computer vision node
  • my_robot_interfaces: custom message types
  • my_robot_commander_cpp: C++ nodes that control the robot

Controlling the arm

Before adding vision, I built a set of ROS2 topics to command the arm directly, so I could test each kind of motion on its own:

  • Named positions: send the arm to a saved pose such as home or pre_pick.
  • Joint targets (forward kinematics): set all seven joint angles.
  • Pose targets (inverse kinematics): give a position and orientation, with an optional Cartesian mode that moves the gripper in a straight line.
  • Gripper: open or close the claw.
ros2 topic pub --once /pose_target my_robot_interfaces/msg/PoseTarget "{x: 0.2, y: 0.3, z: 0.4, roll: 0.2, pitch: 0.4, yaw: 0.0}"

Key decisions

  • Docker for the MoveIt Setup Assistant. The Jazzy version of the assistant crashed spontaneously, so I ran it in a container on ROS2 Humble and used the config files it generated.
  • Custom message types. Joint and pose commands use their own messages in my_robot_interfaces. A joint target must contain exactly seven values, and a pose target has an optional Cartesian-planning flag that defaults to off.
  • Cartesian planning is optional. Forcing a straight-line path constrains the arm and can make some moves fail, so I left it off by default.
  • Longer execution timeout. I raised the allowed_execution_duration_scaling value in the MoveIt controller config to make up for my laptop's slow processing.

Results

The arm picks up all three blocks and places them in the bin, from two different starting layouts. Switching between the test_world.sdf and test_world_2.sdf Gazebo worlds changes where the blocks begin, which shows the arm is following what the camera sees instead of replaying a fixed path.

Known issues

  • Controllers sometimes fail to spawn when the simulation starts. I check them with ros2 control list_controllers and start any inactive ones with the controller manager's spawner.
  • use_sim_time on move_group can't be set from the launch files because of a ROS2 bug, so I set it from the terminal after launch.
